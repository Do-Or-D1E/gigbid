# Data card

GigBid uses two kinds of data. They are kept apart on purpose. This page says which is which, how each was made, and what its limits are. The file formats are in `docs/DATA_CONTRACT.md`.

Short version:

- Everything the agent is evaluated on (personas, portfolios, dev jobs, gold labels, the historical price table) is synthetic and generated by our own scripts.
- Real data (public Kaggle datasets about Upwork) is used in three small ways: to calibrate synthetic prices, to add a sample of real postings to GigSim's live job stream, and as a rough sanity check on freelancer rates. Real data has no gold labels and is not used for scoring.

## Part 1: Synthetic data

### How it is generated

- Entry point: `scripts/generate_data.py`. Helpers are in `scripts/datagen/` (`personas.py`, `persona_specs.py`, `jobs.py`, `job_text.py`, `text_banks.py`, `archetypes.py`, `taxonomy.py`, `code_snippets.py`, `policy.py`, `render_pdf.py`).
- Run: `uv run python scripts/generate_data.py` (or `make data`). The default seed is 4016.
- It is deterministic and offline. No language model and no network are used. The same seed gives byte-identical files (files are written with sorted keys and LF line endings).
- Output: `data/personas/<id>/` (profile, CV as Markdown and PDF, case studies, repos with code, reviews, past proposals, gold files), `data/taxonomy.json`, `data/jobs/historical.jsonl`, `evals/datasets/dev_<id>.jsonl`, `gigsim/seed/stream_jobs.jsonl`, `gigsim/seed/clients.json`, `data/policy_pack/policy_v1|v2.(md|yaml)` and `data/STATS.json`.

### Personas

Three fictional freelancers: `ai_ml`, `fullstack`, `data_analyst`. Names, clients and companies are made up. Counts come from `data/STATS.json` (read it for the current numbers):

| | ai_ml | fullstack | data_analyst |
|---|---|---|---|
| Projects | 20 | 20 | 20 |
| Profile skills | 38 | 35 | 33 |
| Case studies | 15 | 15 | 15 |
| Repositories | 9 | 10 | 11 |
| Client reviews | 16 | 18 | 14 |
| Past proposals | 150 | 150 | 150 |
| CV | 1 | 1 | 1 |

Each project can appear in up to three forms (case study, repo, past proposal or review) written with different words. Skills are often implied and not named, so the retrieval has to work for it. Some repos have a vague README while the code shows the real skill (this is for the multi-vector retrieval variant).

Past proposals carry an outcome (`won`, `replied`, `ignored`). They are bids, not proof of experience. See ADR 0004.

### Job sets

| Set | Where | Size | Use |
|---|---|---|---|
| Dev sets | `evals/datasets/dev_<id>.jsonl` | 200 jobs per persona, with gold labels | Evaluation and tuning |
| Historical jobs | `data/jobs/historical.jsonl` | 1500 closed jobs in 28 categories | Pricing statistics (`get_pricing_stats`) |
| Live stream | `gigsim/seed/stream_jobs.jsonl` | 300 synthetic jobs plus the real postings (see Part 2). The file has 582 lines in total | Jobs released over simulated time by GigSim |
| Clients | `gigsim/seed/clients.json` | See `clients.total` in `data/STATS.json` | Client history and hidden preferences |
| Hold-out stand-in | `evals/holdout/` (git-ignored) | Same size as a dev set, new jobs | Stand-in for a hidden test set |

Dev set plan (from `_plan_dev` in `scripts/datagen/jobs.py`, before duplicates are added). The realised counts are in `data/STATS.json` under `dev`.

| Kind | Planned count per persona |
|---|---|

The tags in `gold.job_type` are `multi_req` (4 or more requirements), `exact_tool`, `vague`, `should_skip`, `scam`, `injection`, `duplicate`, `standard`. `data/STATS.json` has the tag counts for each persona.

### Gold label rules

The label rules are in `decide()` and `relevant_items()` in `scripts/datagen/jobs.py`. Each job is generated for a target action and is regenerated until the rules agree with the target.

- `action` is `skip` when the job is a scam, or when fewer than 60 percent of the required skills are skills the persona owns, or when the budget is under the persona's floor. The floor is `min_project_usd` for fixed jobs and 70 percent of `hourly_rate_usd` for hourly jobs. Otherwise it is `bid`. A job labelled `bid` must also have at least 2 relevant portfolio items.
- `is_scam`: true for jobs built from scam templates.
- `has_injection` and `injection_goal`: true when an injection template was planted. Goals: `leak_contact`, `force_bid`, `insert_phrase`, `price_manipulation`, `exfiltrate_prompt`.
- `requirements`: the canonical skills the job was built from.
- `relevant_items`: portfolio items (not the CV) that share skills with the requirements. Grade 2 when two or more skills overlap or an exact-tool skill overlaps, otherwise grade 1. Up to 5 past proposals that were won or replied, in the same category and with a skill overlap, are added with grade 1. So the gold set can contain past proposals, even though the running system does not use them as proof.
- `fair_price_band`: the 25th and 75th percentile of historical awarded prices for the same category, budget type and complexity bucket, scaled by the job's duration and experience factors. Because the historical table is itself synthetic (with a real-calibrated price level, see Part 2), this band is synthetic too.

### Scam and injection templates

In `scripts/datagen/job_text.py`.

- Scams: 12 clear-cut kinds (Telegram, WhatsApp, direct email, unpaid trial, paid "training", equipment, crypto, overpayment, deposit, credentials, guaranteed returns, free tasks) and 2 soft kinds (off-platform payment, "move to Telegram after hire"). Each kind has two wordings.
- Injections: 15 templates, three for each of the five goals. They are placed at the start, middle or end of the description, or in a "notes" or comment block.
- GigSim's simulated scam clients (`hidden.is_scammer`) answer with a `scam_signal` message.

### Hidden-test stand-in

The real hidden test set is not available to us, so we generate one:

```bash
uv run python scripts/generate_data.py --holdout --seed 777 --out evals/holdout
```

`--holdout` writes fresh dev-style job sets and their clients with a different seed. The personas, taxonomy and historical prices keep the persona seed (`--persona-seed`, default 4016), so the gold labels still point to the real portfolio items. The folder is git-ignored.

### Limitations of the synthetic data

- The text is templated. Sentences come from banks of openers, challenges and results, so style varies less than in real postings. A model can learn these patterns.
- Gold labels follow simple rules (skill coverage and a budget floor). A real freelancer would also weigh client attitude, timing and gut feeling.
- Personas are fictional and each has only 20 projects. Results do not say how GigBid does for a real portfolio.
- Dev sets and the live stream come from the same generator, so they share its habits.
- Scam and injection templates are our guess at what such text looks like. Real attackers vary more.

## Part 2: Real data

All real data comes from public Kaggle datasets about Upwork. The raw downloads are not committed. Only small processed files and aggregate statistics are in `data/real/`. The sources and licences are also in `data/real/SOURCES.md`.

### Datasets used

| ID | Dataset | Licence | What we use it for |
|---|---|---|---|
| A | `asaniczka/upwork-job-postings-dataset-2024-50k-records` | ODC-By 1.0 | Fixed budgets and hourly ranges for price calibration. Real postings (110 in our sample) for GigSim's stream |
| B | `ahmedmyalo/upwork-freelance-jobs-60k` | Apache 2.0 | Same as A, plus real client signals (payment verified, total spent, rating, hires, applicants). Real postings (172 in our sample) |
| C | `asaniczka/freelance-contracts-dataset-1-3-million-entries` | ODC-By 1.0 | Hourly rates and total paid of completed contracts. Aggregates only. Nothing from C is redistributed row by row |
| D | `sarveshchhetri/freelancer-success-earnings-and-churn-prediction` | Licence not stated | A rough sanity check of freelancer hourly rates by primary skill (`data/real/freelancer_rates.json`). Not used anywhere else |

Script: `scripts/import_kaggle.py` (`uv run python scripts/import_kaggle.py --raw ../kaggle_raw`).

### What we did not use

- `asaniczka/all-jobs-on-upwork-200k-plus`: redundant with A.
- `adityammantri/trial-1` (fake job posting detection): the licence is unknown and the download is 207 MB.

### Preprocessing

1. Read each zip file directly. Postings from A have budget and category text mixed into the description, so these are split off first. HTML entities are decoded.
2. Map each posting to one of GigBid's 28 categories by keyword rules (`CATEGORY_RULES` in the script). The first matching rule wins. A posting with no match is dropped.
3. Collect prices per category: fixed budgets (under 100000) from A and B, and hourly rates (hourly range midpoints under 500) from A, B and C.
4. Compute 25th, 50th and 75th percentiles per category and source.
5. Derive base prices for the generator (below) and write `data/real/price_calibration.json`.
6. Sample real postings: postings with a description of acceptable length (A: 250 to 4000 characters, B: 120 to 4000) and a budget. They are sorted by a hash and capped per category (14 for the categories the personas work in, 3 for the others). They are mapped to GigBid's job schema with `connects_cost` computed by the v1 rule. The text is cut to 1600 characters.
7. Write `data/real/real_clients.json` for those postings.
8. `scripts/generate_data.py` appends the real postings to the live stream (`_merge_real`) with a release offset derived from a hash of the job id.

The sample has 282 postings (172 from B, 110 from A) and 272 real clients. C scanned 1292791 contract rows.

### How records are marked

- Every real posting has `real: true`, `source` (the dataset name), `license` and `source_url`.
- Every real client has `real: true`. When the public history comes from B the field `public_history_source` is set.
- A client's hidden preferences cannot be observed in the real data. They are generated from the job id as a seed (`must_have_skills` from the posting's own skills, `budget_ceiling_usd` equal to the posting's budget, random preferences for openings and length, responsiveness). They carry `hidden.synthetic: true`.
- Real clients from A have no public history, so payment verification and spend are empty or false for them.
- Real postings have no gold labels and are not in the dev sets.

### Price calibration

Rule (also written in `method` inside `data/real/price_calibration.json`):

- Fixed base price = real 75th percentile fixed budget, divided by the mean duration factor and the mean experience factor.
- Hourly base rate = real median hourly rate (postings and completed contracts), divided by the mean experience factor.
- A category is calibrated only when it has at least 40 real values. Otherwise the hand-set base stays.
- The generator reads `calibrated_base` in `scripts/datagen/archetypes.py` and keeps the old values as `CATEGORY_PRICE_HAND`.

Why the 75th percentile for fixed prices: the real median is dominated by tiny tasks (the 25th percentile is 15 to 50 USD in many categories), while our personas aim at mid-size projects. The upper quartile is a closer match for a typical job of that kind. This is a judgement, not a measured fact. Another choice would give other prices.

Examples (all numbers from `data/real/price_calibration.json`). Each pair is `[fixed base USD, hourly base USD per hour]`. The base is multiplied by duration and experience factors per job, so it is not a job price by itself.

| Category | Hand-set base | Calibrated base | Real fixed p75 (n) | Real hourly median (n) |
|---|---|---|---|---|
| LLM & RAG Applications | [2200, 58] | [890, 30] | 1000 (657) | 30 (3155) |
| ML Model Development | [1800, 52] | [534, 32] | 600 (579) | 32.5 (1798) |
| Web App Development | [2400, 45] | [801, 25] | 900 (2991) | 25 (21172) |
| Business Intelligence & Dashboards | [900, 32] | [267, 37] | 300 (459) | 37.5 (5646) |
| Data Pipelines & ETL | [1100, 36] | [445, 35] | 500 (71) | 35 (988) |
| Writing & Translation | [200, 18] | [356, 25] | 400 (4517) | 25 (35741) |

Most fixed prices go down, because the hand-set values were too high. Some go up (Writing & Translation). One category, MLOps & Deployment, has only 9 real fixed budgets, so its fixed base stays hand-set (1700) while its hourly base is calibrated (55 to 44).

### Limitations of the real data

- Category mapping is by keywords. Some postings land in a wrong category and some are dropped.
- Real postings have no gold labels, so they cannot be scored. They only make the live stream more realistic.
- Dataset A has no client history, and B's client signals are a snapshot from when the data was collected.
- Hidden client preferences for real clients are synthetic, so outcome simulation on real postings is partly made up.
- The datasets are from 2024 and earlier. Prices may have moved.
- Dataset D has an unknown collection method. Its numbers are only a sanity check.
- Real descriptions can contain odd characters. In an early version, `str.splitlines()` split JSON lines on Unicode line separators inside descriptions. Code that reads JSON Lines with real text (`rag/ingest/loaders.py`, `scripts/generate_data.py`) now splits on a plain newline only.
